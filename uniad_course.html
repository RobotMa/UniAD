The Big Picture

What Does UniAD Actually Do?

Before any code — what problem is this solving, and why does it matter?

Most self-driving systems are a chain of separate programs: one detects objects, another tracks them, another plans a route. Each program passes its output to the next. But errors compound — a bad detection makes a bad plan.

💡
UniAD's Core Idea

Train all tasks together, end-to-end, so that every part of the network learns to help the final goal: safe driving. Perception exists to serve planning.

The 5 Tasks UniAD Solves — Together

🎯
Tracking
Find every car, pedestrian, and cyclist — and follow them across frames over time.
🗺️
Map Segmentation
Detect lane lines, crossings, and road boundaries as a top-down map.
🔮
Motion Forecasting
Predict where every agent will be 3 seconds from now — multiple possible futures.
🌫️
Occupancy Prediction
Which grid cells will be occupied by moving objects in the future?
🚗
Planning
Generate a safe 3-second trajectory for the ego vehicle to follow.

The Shared Foundation

Bird's Eye View — Seeing the World from Above

Six perspective cameras. One top-down map. This is how UniAD creates a shared "canvas" for all its tasks.

Each camera sees the world in perspective. But to reason about where things are, it helps to think top-down — like a city map. UniAD uses BEVFormer to transform camera images into a BEV feature map.

🧭
The "Unfolding" Analogy

Imagine taking 6 photos around a room and stitching them into a top-down floor plan. BEVFormer does this mathematically, using deformable attention to project image features onto a 200×200 grid.

Code ↔ English: The Forward Pass

CODE (uniad_track.py) 
# img shape: [B, T, N, C, H, W]
# B=batch, T=time frames, N=6 cameras
bev_embed, bev_pos = self.pts_bbox_head(
    mlvl_feats,   # multi-scale img features
    bev_queries,  # learnable BEV grid queries
    prev_bev,     # previous frame's BEV
)
# bev_embed: [B, 200*200, 256]
PLAIN ENGLISH

The input is a stack of images: batch × time × 6 cameras.

The BEV head takes multi-scale image features (detail at different zoom levels)...

...and 40,000 learnable "questions" — one for each cell in the 200×200 top-down grid.

It also takes the previous frame's BEV map for temporal continuity (like short-term memory).

Output: 40,000 feature vectors — one per grid cell — each 256 numbers long.

Why Temporal History Matters

1
Frame N-2: car is here

The BEV map stores a feature snapshot. queue_length=3 in the config.

2
Frame N-1: car moved a little

BEVFormer warps the previous BEV using ego-motion (where the car drove), aligning them in the same coordinate frame.

3
Frame N: fuse for richer BEV

Current frame features are combined with aligned history. Objects that were briefly occluded can still be reasoned about.

03
Perception

Tracking — Knowing Who's Around You

Detect objects in 3D space, and keep following them across time — even when they disappear momentarily.

Traditional object detectors find things in each frame independently. But a self-driving car needs to track agents over time — "that's the same blue sedan I saw 3 frames ago, it's now 8 meters closer." UniAD uses a transformer-based tracker with a memory bank.

num_query=900 Up to 900 objects can be tracked simultaneously in one scene
miss_tolerance=5 An object can vanish for 5 frames before being dropped from the tracker
embed_dims=256 Each object is represented as a 256-dimensional feature vector (query)
score_thresh=0.2 Only objects detected with >20% confidence are kept

# QIM = Query Interaction Module
# Decides which tracks survive each frame
qim_args = dict(
    qim_type="QIMBase",
    merger_dropout=0,
    update_query_pos=False,
    fp_ratio=0.3,   # false positive ratio
    random_drop=0.1,  # drop 10% of tracks randomly
)
PLAIN ENGLISH

The Query Interaction Module is the bouncer at the door — it decides which tracked objects continue to the next frame.

30% of "detections" during training are deliberately wrong (false positives), to teach robustness.

10% of real tracks are randomly dropped during training, so the model learns to recover from lost tracks.

This makes the tracker much more robust in the real world where objects suddenly appear and disappear.

Two-Stage Training: Why It Matters

1
Stage 1 — Perception Only

Train only Track Head + Map Head. The network learns to reliably detect objects before worrying about planning. Uses 5 frames of history (queue_length=5). Result: AMOTA 0.394.

2
Stage 2 — End-to-End

Unfreeze everything and add Motion, Occ, and Planning heads. Now the tracker learns what features are actually useful for planning. Uses 3 frames (queue_length=3).

🔑
Why Stage 1 First?

Without a stable perception backbone, training everything at once causes the model to "collapse" — the planner can't learn if it keeps getting garbage detections. Stage 1 provides a warm start.

04
Prediction

Map & Motion — Reading Roads, Predicting Futures

Two tasks that feed each other: map tells motion where roads are, motion tells planning where agents will go.

Map Segmentation (Seg Head)

The map head reads the BEV feature map and outputs a vectorized road map — lane dividers, crosswalks, and road edges as geometric shapes. It uses a DETR-style query approach: 100 queries, each predicting one lane element.

CODE (uniad_e2e.py) 
if self.with_seg_head:
    losses_seg, outs_seg = \
        self.seg_head.forward_train(
            bev_embed,   # the shared top-down map
            img_metas,
            gt_lane_labels,
            gt_lane_bboxes,
            gt_lane_masks,
        )
    losses_seg = self.loss_weighted_and_prefixed(
        losses_seg, prefix='map'
    )
PLAIN ENGLISH

If the map head exists, run it on the BEV feature map.

Give it the ground-truth lane labels, bounding boxes, and masks to learn from.

Get back the map loss (how wrong our lane predictions were)...

...and the map output (predicted lanes) which feeds into the Motion Head.

Prefix the loss with "map." so we can tell it apart from the tracking or planning losses.

Motion Forecasting (Motion Head)

For each tracked agent, the motion head predicts 6 possible trajectories 3 seconds into the future. It uses a transformer decoder that attends to both the BEV map and the map head's lane outputs.

predict_steps=12 Predict 12 time steps at 0.5s each = 6 seconds into the future
num_anchor=6 6 possible futures per agent — "multimodal" prediction
minADE: 0.71m The best prediction is on average only 0.71m off — state of the art

How Motion Uses Both BEV and Map

1
Input: Track queries + BEV embed + map output

The motion head receives the 256-dimensional feature for each tracked agent, the full BEV, and the predicted lane structure.

2
Agent-to-agent attention

Each agent's query attends to all other agents — "where is the car ahead of me going?" This enables socially-aware predictions.

3
Agent-to-map attention

Queries also attend to nearby lane features: "is there a left-turn lane here?" This constrains predictions to road-plausible trajectories.

4
Output: traj_query for occupancy

The refined trajectory queries are passed to the Occ Head — not just the predicted coordinates, but the full feature vectors, so occupancy can learn from motion context.

05
Scene Understanding

Occupancy — What Space Will Be Taken?

Instead of tracking individual objects, think about space: which grid cells will be dangerous in 2 seconds?

Tracking gives you a list of objects with IDs. But the planner needs to know about space — "don't drive into that cell." The occupancy head predicts a 200×200 grid for each of the next 4 time steps, answering: "will this square meter be occupied?"

💡
Objects vs. Space

Tracking is like knowing "Bob's car is at position (x,y)." Occupancy is like coloring a map: "these 12 cells will be red (dangerous) in 2 seconds." The planner prefers the map — it's safer to reason about space than about individual objects.

Occ Head Architecture

1
Inputs: BEV + motion queries

Takes the 200×200 BEV feature map plus the trajectory queries from the Motion Head. Each tracked agent contributes its predicted future positions.

2
Transformer decoder over BEV

receptive_field=3 past frames + n_future=4 future frames. The decoder attends to the BEV and agent trajectory queries simultaneously.

3
Instance segmentation in future

Not just "is this cell occupied" but which tracked instance will be there. This enables collision attribution: "car #3 caused this collision."

4
Output to planning

The predicted occupancy map is the safety constraint for the planner — the planned trajectory must avoid all high-occupancy cells.

Code ↔ English: Running the Occ Head

CODE (uniad_e2e.py) 
# Edge case: no tracked objects in scene
if outs_motion['track_query'].shape[1] == 0:
    outs_motion['track_query'] = \
        torch.zeros((1, 1, 256)).to(bev_embed)
    outs_motion['traj_query'] = \
        torch.zeros((3,1,1,6,256)).to(bev_embed)

losses_occ = self.occ_head.forward_train(
    bev_embed, outs_motion,
    gt_segmentation=gt_segmentation,
    gt_instance=gt_instance,
)
PLAIN ENGLISH

Sometimes a scene has no tracked objects at all (empty road). Protect against a crash: fill with dummy zero-vectors.

A 1×1×256 dummy track and a 3-layer trajectory query of all zeros keeps the shape valid.

Then run the occupancy head with the real BEV features and the motion outputs.

Ground truth: what cells were actually occupied (segmentation) and which instance was there.

The Final Decision

Planning — Choosing Where to Go

Everything so far was in service of this: generate a safe 3-second path, guided by a high-level command.

The planning head takes the BEV features, the motion head's scene understanding, and a navigation command (turn left / go straight / turn right). It outputs a sequence of 6 waypoints — where the car should be at each 0.5-second step.

planning_steps=6 6 waypoints × 0.5s each = 3 seconds of planned trajectory
navi_embed 3-entry embedding: each command (left/straight/right) becomes a 256-dim vector
avg.Col=0.29% Planned trajectories collide with obstacles only 0.29% of the time — state of the art
use_col_optim Optional: post-processing that nudges waypoints away from occupied cells using gradient descent

Code ↔ English: The Planning Head

CODE (planning_head.py) 
# navi_embed: turn left/straight/right → vector
self.navi_embed = nn.Embedding(3, embed_dims)

# reg_branch: predict 6 (x,y) waypoints
self.reg_branch = nn.Sequential(
    nn.Linear(embed_dims, embed_dims),
    nn.ReLU(),
    nn.Linear(embed_dims, planning_steps * 2),
)
# output shape: [B, 6, 2] = 6 (x,y) points
PLAIN ENGLISH

The navigation command (0, 1, or 2) is turned into a 256-number vector. "Turn left" looks different from "go straight" in this space.

A small neural network (two linear layers with a ReLU in between)...

...takes the combined BEV + motion + command feature and outputs 12 numbers.

12 = 6 steps × 2 coordinates (x, y). These are the planned waypoints in the car's local frame.

The Loss Hierarchy

UniAD optimizes all tasks simultaneously. Each task's loss is weighted by the task_loss_weight dict:

CODE (uniad_e2e.py) 
task_loss_weight = dict(
    track=1.0,
    map=1.0,
    motion=1.0,
    occ=1.0,
    planning=1.0
)
# total_loss = sum of all weighted task losses
for k, v in losses.items():
    losses[k] = torch.nan_to_num(v)
PLAIN ENGLISH

Each of the 5 tasks contributes equally to the total training signal.

If you want the model to prioritize planning safety, increase planning's weight to 2.0.

The final line is a safety net: if any loss becomes NaN (a math error), replace it with 0 so training doesn't crash.
